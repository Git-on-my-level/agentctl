## Finding 1: known pre-receipt coverage gap; retain the approved boundary

The reported lost-receipt window is real. It is outside the published retained
record coverage claim, rather than a promise this query currently makes:

- [Published coverage schema](https://github.com/Git-on-my-level/agentctl/blob/3239b9359d02be4ebf45ef38a219b112f287bb3e/schemas/children-result.schema.json#L33)
  fixes coverage to `retained_attributed_executions_only`.
- [Published remote receipt limitation](https://github.com/Git-on-my-level/agentctl/blob/3239b9359d02be4ebf45ef38a219b112f287bb3e/docs/child-work.md#L110)
  explicitly excludes remote launches whose receipts were lost before local
  forwarding admission, and requires identical-key recovery.
- [Remote transport error semantics](https://github.com/Git-on-my-level/agentctl/blob/3239b9359d02be4ebf45ef38a219b112f287bb3e/cmd/agentctl/remote.go#L122)
  preserve retryable uncertainty and direct identical-key recovery. They do not
  certify that launch did not happen.
- [Forwarding binding validation](https://github.com/Git-on-my-level/agentctl/blob/3239b9359d02be4ebf45ef38a219b112f287bb3e/internal/model/delegation.go#L191)
  requires proven typed remote execution and host IDs. A local row invented
  before the receipt is not an ordinary valid forwarding row.

Recommendation: preserve the approved claim in this batch. A future write-ahead
admission contract should separately define pending/uncertain/refused states,
caller ownership, cancellation/crash recovery and identical-key convergence
without storing prompts/session IDs or fabricating remote identity. The parent
must not interpret an empty retained index as proof of no remote launch after
an uncertain transport result. If global pre-receipt Stop coverage is required
for merge, it needs an explicit contract decision; this batch does not silently
expand remote lifecycle authority.

## Finding 4: existing graph retention policy; do not weaken it here

The review correctly observes that collected parent-linked graphs remain
protected. That is the inherited safety policy, explicitly preserved by PR147:

- [Base branch graph construction](https://github.com/Git-on-my-level/agentctl/blob/4e9167e323996cc353f176bbf4d0d233d059df21/internal/store/retention.go#L321)
  already links `ParentExecutionID`.
- [Base branch deletion guard](https://github.com/Git-on-my-level/agentctl/blob/4e9167e323996cc353f176bbf4d0d233d059df21/internal/store/retention.go#L336)
  already protects every graph-linked execution, independent of acknowledgement.
- The published PR body's Remaining limits explicitly preserved collected
  parent-linked graphs and deferred graph-retention policy.

Automatic attribution creates more parent edges, so the retention-growth concern
is real even though the guard predates this PR. The published scope accepted
preserving that guard and deferring a graph collection policy.

Recommendation: retain this deletion guard. Define lifecycle-aware collection
as separate graph-retention work, including replay, promotion, external refs,
partial retention and mixed-version atomicity. Do not delete acknowledged graphs
by relaxing this one condition. The new collected-child cleanup cases explicitly
lock in the current policy while proving unrelated acknowledged unkeyed rows
remain eligible. Finding2 must be fixed precisely so the existing guard works
after legacy projection rewrites.
